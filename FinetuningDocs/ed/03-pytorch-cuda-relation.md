# 03. PyTorch와 CUDA의 관계 — 그리고 실무자는 무슨 언어를 쓰나

> **질문 1**: 파이썬(PC통제)에서 쿠다(GPU통제)를 돌린다고 보면 되나?
> **질문 2**: PyTorch의 cuda는 파이썬과 CUDA를 호환시키는 라이브러리인가?
> **질문 3**: 실제 기업에서 파인튜닝하는 사람은 Python과 C++ 중 뭘 다루나?

## 한 줄 답

파이썬은 CUDA를 **직접 부르지 않는다**. 중간에 PyTorch C++ 층이 있다.
그리고 실무 파인튜닝은 **파이썬 ~99%** 다.

---

## 1. 파이썬은 CUDA를 직접 돌리지 않는다

**맞은 부분**: "CPU가 지휘하고 GPU가 일한다"는 구도는 정확하다.
GPU는 스스로 시작하지 못하고 항상 CPU 쪽에서 시켜야 움직인다.

**정정 2가지:**

**(1) 파이썬은 PC를 통제하지 않는다.**
파이썬도 CPU 위에서 도는 프로그램 하나일 뿐이고, 통제는 OS가 한다.
파이썬의 위치는 "지휘자"가 아니라 **"지시서를 작성하는 사람"** 이다.

**(2) 파이썬은 CUDA 코드를 한 줄도 실행하지 않는다.**
파이썬은 `__global__` 같은 CUDA 문법을 이해하지 못한다. 반드시 C++ 층이 중간에 있다.

```
파이썬        x.to("cuda"); model(x)     <- 무엇을 할지 지시
   |
PyTorch C++   libtorch_cuda.so           <- ★ 실제로 CUDA를 호출하는 주체
   |
CUDA 런타임   cudaMalloc, cudaLaunchKernel
   |
드라이버 -> GPU 하드웨어
```

> "파이썬이 CUDA를 돌린다"가 아니라
> **"파이썬이 PyTorch에게 시키고, PyTorch가 CUDA를 돌린다."**

### 덧: 비동기

파이썬이 `model(x)`를 실행하면 **GPU 작업이 끝나기를 기다리지 않고 즉시 다음 줄로 넘어간다.**
지시만 큐에 넣고 간다. 결과가 실제로 필요한 순간(`.item()`, `print()`)에야 멈춰서 기다린다.
**GPU 성능 측정이 자주 틀리는 게 이것 때문이다** (`cudaDeviceSynchronize`가 필요한 이유).

## 2. 창구 vs 공장

`torch.cuda`(파이썬 모듈)와 `libtorch_cuda.so`(컴파일된 실체)는 이름이 비슷하지만 완전히 다르다.

| | `torch/cuda/*.py` | `libtorch_cuda.so` |
|---|---|---|
| 크기 | **0.3 MB** (24개 파일) | **435 MB** |
| 성격 | 파이썬 ↔ CUDA **연결 창구** | PyTorch가 **직접 짠 GPU 구현체** |
| 내용 | `device_count()`, `memory_allocated()`, `synchronize()` 등 145개 | GPU 커널 심볼 **8,530개**, `at::native` 구현 **11,125개** |
| "호환 라이브러리"인가 | ✅ 맞다 | ❌ 아니다 |

`torch.cuda`의 함수 목록을 보면 `current_device`, `get_device_name`, `memory_allocated`처럼
전부 **GPU를 조회하고 관리하는 창구**다. **계산 기능은 하나도 없다.**

> **창구는 `torch.cuda`(파이썬), 공장은 `libtorch_cuda.so`(C++).**

### 왜 PyTorch가 직접 GPU 코드를 짜야 했나

cuBLAS/cuDNN만 있으면 될 것 같지만 안 된다.

- **NVIDIA가 제공하는 것**: 행렬곱, 합성곱, FFT 등 **표준 연산 몇십 개**
- **PyTorch에 필요한 것**: `relu`, `softmax`, `layer_norm`, 인덱싱, 브로드캐스팅,
  각종 손실 함수… **수천 개의 연산**

NVIDIA는 `F.gelu`를 만들어주지 않는다. 그래서 **PyTorch 팀이 수천 개를 전부 CUDA로 직접 작성**했고,
그게 8,530개 커널 심볼의 정체다.

## 3. 이 프로젝트는 "CUDA 없는 PyTorch"인가

단어를 하나 고쳐야 한다. **"쿠다 없는"이 아니라 "쿠다가 있지만 쓰지 않는"** PyTorch다.
별도 버전을 깔지 않고, 지금 설치된 그대로 CPU 경로로만 돌린다.
`libtorch_cpu.so`가 실행되고 `libtorch_cuda.so`는 디스크에 누워만 있다.

**학습에는 아무 지장이 없다.** PyTorch API는 CPU든 GPU든 **완전히 동일**하다.

```python
device = "cuda" if torch.cuda.is_available() else "cpu"   # 관용구
model = model.to(device)
x = x.to(device)
```

이 코드는 이 서버에서 `cpu`로 떨어지지만, GPU 장비에 올리면 **한 글자도 안 고치고** 돌아간다.
배우는 내용은 100% 그대로 이전된다. 차이는 오직 **속도**뿐.

> ⚠️ **가장 흔한 GPU 에러**: 모델과 데이터의 device가 다르면
> `Expected all tensors to be on the same device`. 물리적으로 다른 칩의 메모리이기 때문이다.

## 4. 실무자는 Python과 C++ 중 뭘 다루나

**압도적으로 파이썬이다.** 파인튜닝을 업으로 하는 사람은 C++을 거의 만지지 않는다.

| 역할 | 주 언어 | 인원 비중 | 하는 일 |
|---|---|---|---|
| **ML 엔지니어 / 파인튜닝** | **파이썬 ~99%** | 다수 | 데이터 구축, 학습 스크립트, 하이퍼파라미터, 평가 |
| 추론 최적화 / 서빙 | 파이썬 + 일부 C++ | 소수 | 양자화, TensorRT, vLLM, llama.cpp |
| 커널 / 프레임워크 개발 | **C++ / CUDA** | 극소수 | PyTorch 자체 개발, 새 연산 구현 |

"CUDA에게 시켜서 GPU를 쓰는 사람"은 첫 줄이고, 그 사람은 **CUDA를 직접 부르지 않는다.**
`.to("cuda")` 한 줄만 쓰고 나머지는 PyTorch가 알아서 한다.
CUDA를 직접 짜는 건 셋째 줄, NVIDIA나 Meta의 소수 인력이다.

### 진짜 어려운 건 언어가 아니다

파인튜닝 실무의 난이도는 **그 위의 판단**에 있다.

| 항목 | 왜 어려운가 |
|---|---|
| **데이터 품질** | 대부분의 실패는 코드가 아니라 데이터에서 온다 |
| **메모리 관리** | OOM 시 batch를 줄일지, 층을 얼릴지, gradient accumulation을 쓸지 판단 |
| **평가 설계** | "좋아진 것 같다"가 아니라 숫자로 증명하기 |
| **분산 학습** | GPU 여러 장에 어떻게 나눌 것인가 |

전부 파이썬으로 하는 일이고 C++ 지식은 필요 없다.
다만 **"GPU 메모리가 CPU와 별개"라는 개념**은 반드시 알아야 한다
(→ [02번 문서 4절](./02-cuda.md)). 그래야 OOM 앞에서 무엇을 줄일지 판단할 수 있다.

### 중간 지대: Triton

**파이썬 문법으로 GPU 커널을 작성**하면 CUDA로 컴파일해준다.
이 venv에도 641 MB로 깔려 있다(GPU가 없어 역시 쉬는 중).
예전엔 C++ 전문가만 하던 커널 작성이 파이썬 사용자에게 열렸지만,
파인튜닝 담당자가 여기까지 갈 일은 드물다.
