# 04. 옵티마이저 — SGD, Adam, 그리고 학습률

> **다룬 질문**
> - AdamW가 SGD보다 빠른가? (→ 실험 결과 **반대로 나왔다**)
> - `lr=2e-5`는 무슨 수식인가? 상수들은 뭔가?
> - Adam이 애초에 뭔가?
> - SGD는 뭔가?

## 한 줄 요약

**옵티마이저는 "그래디언트를 받아 파라미터를 얼마나 움직일지" 정하는 규칙**이다.
SGD는 `p -= lr*g` 그 자체고, Adam은 여기에 관성과 파라미터별 정규화를 더한 것이다.

---

## 0. 먼저: `2e-5`는 수식이 아니다

지수 표기법이고, `e-5`는 "×10⁻⁵" = **소수점을 왼쪽으로 5칸**이다.

| 표기 | 값 |
|---|---|
| `2e-5` | **0.00002** |
| `1e-3` | 0.001 |
| `1e-8` | 0.00000001 |
| `3e4` | 30000 (부호 없으면 오른쪽) |

`2e-5 == 0.00002` → `True`. 0을 세다 틀리지 않으려고 쓰는 표기일 뿐이다.

## 1. SGD — Stochastic Gradient Descent

### `02_autograd.py`에서 이미 구현했다

```python
param -= lr * param.grad          # 이 한 줄이 SGD 전부
```

50스텝 돌려 `torch.optim.SGD`와 비교하면 **비트 단위로 동일**하다.

```
수동: w=3.1072463989  b=1.6838485003
SGD : w=3.1072463989  b=1.6838485003     equal: True
```

`SGD`의 `state`는 **0개**다. 기억하는 게 없다. 그래서 파라미터당 4 B만 쓴다.

### 이름 쪼개기

**Gradient Descent (경사하강)** — 기울기 반대 방향으로 한 걸음.
안개 속 산에서 발밑 경사만 보고 아래로 딛는 것.

**Stochastic (확률적)** — 전체 데이터가 아니라 **무작위 일부(배치)로 근사**한다.

데이터 2,000개 실측. 전체로 계산한 그래디언트를 참값으로 두고 비교:

| 배치 크기 | 참값과의 코사인 유사도 |
|---|---|
| 8 | **0.6075** ± 0.114 |
| 32 | 0.8637 ± 0.057 |
| 128 | 0.9667 ± 0.017 |
| 512 | 0.9948 ± 0.002 |
| 2000 (전체) | 1.0000 ± 0.000 |

배치 8의 그래디언트는 참값과 방향이 **0.61밖에 안 맞는다.** 이 무작위 오차가 `S`다.

### 그런데 부정확한 쪽이 이긴다

샘플 40,000개를 처리하는 **동일 연산 예산**으로 비교:

| 배치 크기 | 갱신 횟수 | 최종 loss |
|---|---|---|
| 8 | **5,000** | 0.010348 |
| 32 | 1,260 | 0.010048 |
| 128 | 320 | 0.009952 |
| **512** | 80 | **0.009943** ← 최적 |
| 2000 (full-batch) | **20** | **0.117182** ← 11배 나쁨 |

> **정확한 걸음 20번보다 대충 맞는 걸음 5,000번이 멀리 간다.**
> 이게 딥러닝이 미니배치로 학습하는 이유다.

단, **작을수록 좋은 건 아니다.** 위에서 최적은 512였다.
너무 작으면 노이즈가 과하고 병렬 처리 능력도 못 쓴다.

### 짚어둘 것: `torch.optim.SGD`는 "확률적"과 무관하다

| 담당 | 역할 |
|---|---|
| `DataLoader(batch_size=8)` | **Stochastic** — 데이터를 무작위로 잘라 공급 |
| `torch.optim.SGD` | **Gradient Descent** — `p -= lr*g` |

엄밀히는 원래 SGD가 샘플 1개씩 쓰는 방식이고, 실제로 쓰는 건 mini-batch SGD인데
관행적으로 다 SGD라고 부른다.

## 2. Adam — SGD의 두 가지 병을 고친 약

### 병 1: 그래디언트가 흔들려 갈팡질팡한다

**약 = Momentum (1964)** — 과거 방향을 기억해 평균낸다. 흔들리는 성분은 상쇄된다.

```
m = β₁·m + (1−β₁)·g          ← Adam의 m
```

### 병 2: 파라미터마다 적정 보폭이 다른데 lr은 하나다

**이게 더 심각하다.** `w1`은 2.0, `w2`는 0.003을 찾아야 하고
입력 스케일이 1000배 달라 **그래디언트가 1124배 차이** 나는 문제:

```
w1의 그래디언트:    −2.55
w2의 그래디언트: −2862.02
```

**SGD (2000스텝, lr을 바꿔가며):**

| lr | loss | w1 (→2.0) | w2 (→0.003) | 판정 |
|---|---|---|---|---|
| 1e-2 | nan | — | — | **발산** |
| 1e-4 | nan | — | — | **발산** |
| 1e-6 | 0.5937 | 0.0012 | 0.004363 | **w1 미학습** |
| 1e-8 | 0.5944 | 0.0000 | 0.004364 | **w1 미학습** |

**작동하는 lr이 존재하지 않는다.** 크면 폭발, 작으면 w1이 안 움직인다. 중간이 없다.

**AdamW:** lr=1e-2 → loss 0.000147, w1=1.9893, w2=0.002982. **성공.**

> ⚠️ 첫 실험은 `x2 = 1000·x1`로 두 입력이 종속이라 해가 무한히 많았다(설계 오류).
> 위 결과는 독립 입력으로 다시 짠 것이다.

**약 = RMSProp (2012)** — 각 파라미터의 그래디언트 크기를 따로 추적해 그 크기로 나눈다.

```
v = β₂·v + (1−β₂)·g²         ← Adam의 v
```

### Adam = 두 약을 합친 것

```
m = β₁·m + (1−β₁)·g          ← Momentum: 방향을 매끄럽게
v = β₂·v + (1−β₂)·g²         ← RMSProp:  크기를 파라미터별로 정규화

m̂ = m / (1 − β₁^t)           ← 편향 보정 (m,v를 0에서 시작했으므로)
v̂ = v / (1 − β₂^t)

θ = θ − lr · m̂ / (√v̂ + ε)
```

### 이름 해부

통계의 **적률(moment)**:

| | 뜻 | Adam에서 |
|---|---|---|
| 1차 moment | 평균 | `m` = 그래디언트의 평균 |
| 2차 moment | 제곱의 평균 | `v` = 그래디언트²의 평균 |

이 적률을 **추정(estimation)** 하고 그걸로 학습률을 **적응(adaptive)** 시킨다
→ **AD**aptive **M**oment estimation.

### 계보

| 연도 | 이름 | 기여 |
|---|---|---|
| 1951 | SGD | `p -= lr*g` |
| 1964 | Momentum | 과거 방향 기억 (→ `m`) |
| 2011 | AdaGrad | 파라미터별 학습률 (누적이라 계속 작아지는 문제) |
| 2012 | RMSProp | 이동평균으로 개선 (→ `v`) |
| **2014** | **Adam** | **Momentum + RMSProp 결합** |
| 2017 | **AdamW** | weight decay 구현 수정 |

**AdamW의 W = Weight decay.** 원래 Adam은 weight decay를 그래디언트에 더했는데
그러면 `√v̂`로 나뉘며 효과가 왜곡된다. AdamW는 분리해서 따로 적용한다.
**파인튜닝에서는 항상 AdamW를 쓴다.**

## 3. 손으로 구현해 torch와 일치시킨 검증

위 5줄 공식 그대로 짜서 `torch.optim.AdamW`와 비교:

| step | grad | m̂ | v̂ | 이동량 | torch와 일치 |
|---|---|---|---|---|---|
| 1 | −39.382 | −39.382 | 1550.9 | +0.010000 | **True** |
| 3 | −38.982 | −39.168 | 1535.2 | +0.009996 | **True** |
| 5 | −38.582 | −38.940 | 1519.6 | +0.009989 | **True** |

```
torch w = 0.81451577
수동  w = 0.81451577      allclose(atol=1e-7) = True
```

**Adam에 비밀은 없다.** 위 5줄이 전부고, 나머지는 그걸 빠르게 돌리는 C++ 코드다.

## 4. ★ 왜 이동량이 항상 lr 근처인가

`m̂`은 그래디언트의 평균, `√v̂`는 그래디언트 크기의 평균이다.
그래디언트가 일정하면 **둘이 거의 같아서 나누면 ±1**이 된다.

```
실측: m̂ = −38.940,  √v̂ = 38.983,  비율 = −0.9989
      lr(0.01) × −0.9989 = −0.009989   ← 실제 이동량과 일치
```

그래디언트가 −39든 −3900이든 **비율은 항상 ±1** → 이동량은 `lr`로 고정.

### 이것이 처음 실험의 반전을 설명한다

`y = 3x + 2` 맞히기, 200스텝, lr=0.01, 동일 초기값:

| 옵티마이저 | 최종 loss | w | b |
|---|---|---|---|
| SGD | 0.006827 | 3.0686 | 1.7984 |
| SGD+momentum | **0.000000** | **3.0000** | **2.0000** |
| **AdamW** | **3.388440** ← 최악 | 2.2388 | 2.2884 |

200스텝 × 0.01 = **최대 2.0밖에 못 간다.** 그런데 w는 0.7645에서 3.0까지
**2.2355를 가야 했다. 애초에 도달 불가능.**

검증 — lr을 올리면 수렴한다:

| lr | 최종 loss | w | b |
|---|---|---|---|
| 0.01 | 3.388440 | 2.2388 | 2.2884 |
| 0.05 | 0.048308 | 2.8046 | 2.5042 |
| 0.1 | 0.010927 | 2.9073 | 2.2267 |
| 0.5 | **0.000947** | 2.9769 | 2.0412 |

> **장난감 문제에서는 SGD가, 실제 모델에서는 Adam이 이긴다.**
> "Adam이 항상 빠르다"는 통념은 틀렸다. 같은 성질이 상황에 따라 단점도 장점도 된다.

---

## 5. ★ 그래서 lr=2e-5 는 "이동량 예산"이다

Adam에서 **`lr`은 사실상 "스텝당 최대 이동량"** 이다.

| lr | 의미 | 쓰는 곳 |
|---|---|---|
| `1e-3` | 스텝당 최대 0.001 이동 | **처음부터 학습**(from scratch) |
| `2e-5` | 스텝당 최대 0.00002 이동 | **파인튜닝** |

`2e-5` = **"가중치 하나를 한 스텝에 0.00002 이상 움직이지 마라"**

사전학습으로 이미 잘 맞춰진 가중치를 망가뜨리지 않으려고 **의도적으로 작게** 주는 것이다.
크게 주면 모델이 원래 알던 한국어 지식을 잊는다(catastrophic forgetting).

**마법의 숫자가 아니라 이동량 예산이다.**

## 6. 상수들의 출처 — 성격이 셋으로 나뉜다

`torch.optim.AdamW(params).defaults` 실측:

| 상수 | 값 | 역할 | **성격** |
|---|---|---|---|
| `β₁` | 0.9 | `m`을 90% 과거 + 10% 현재로 → 최근 ~10스텝 기억 | **관행** (Adam 논문 2014) |
| `β₂` | 0.999 | `v`를 99.9% 과거로 → 최근 ~1000스텝 | **관행** |
| `ε` | 1e-8 | `√v̂`가 0일 때 나눗셈 폭발 방지 | **안전장치** |
| `weight_decay` | 0.01 | 가중치가 커지는 것에 벌점 | 관행 |
| `lr` | **2e-5** | 스텝당 이동량 예산 | **관행** (파인튜닝 1e-5~5e-5) |
| warmup | 10% | 초반 lr을 0부터 올림 (초기 그래디언트 불안정) | 관행 |
| `batch_size` | **8** | — | **우리가 계산** (RAM 1.4 GB) |
| `max_seq_len` | **128** | — | **우리가 계산** |
| `freeze_below` | **8** | — | **우리가 계산** (110M×16B=1,760MB > 1.4GB) |
| `epochs` | 2~3 | — | 판단 (2천 쌍이라 그 이상은 과적합) |
| `scale` | 20 | 손실 함수 온도 | 관행 (→ 07번에서) |

### 정직하게

**관행에 속한 값들은 유도된 게 아니다.** 논문에서 잘 됐고 이후 많은 사람이 써서
잘 되는 게 확인된 값이다. `β₂ = 0.999`가 왜 0.998이 아닌지에 대한 깔끔한 이론은 없다.

실무에서 실제로 조절하는 건 사실 **`lr` 하나**이고 나머지는 기본값을 쓴다.
표에서 **"우리가 계산"** 인 4개가 이 프로젝트에서 근거를 갖고 정한 값들이다.

## 7. 메모리 — Adam의 대가

| | 파라미터당 | 비고 |
|---|---|---|
| 가중치 | 4 B | 동결해도 안 줄어듦 (순전파에 필요) |
| 그래디언트 | 4 B | 동결하면 없어짐 |
| **Adam 상태 (`m`, `v`)** | **8 B** | 동결하면 없어짐 |
| **합계** | **16 B** | |

| 옵티마이저 | 파라미터당 메모리 |
|---|---|
| SGD | **4 B** |
| SGD + momentum | 8 B |
| **AdamW** | **16 B** |

이게 PLAN.md의 `110M × 16B = 1,760 MB` 계산이고, 여유 RAM 1.4 GB인 이 서버에서
전체 파인튜닝이 불가능한 이유다. **"메모리를 내고 안정성을 산" 거래다.**

## 이 프로젝트와의 연결

- Stage 3의 `lr=2e-5`는 5절 그대로.
- `--freeze-below 8`로 줄어드는 건 7절의 12 B(그래디언트 4 + 상태 8)다.
- **`batch_size=8`은 RAM 때문에 강제된 값이고 이상적이지 않다.**
  1절 실험에서 최적은 512였다. 게다가 07번 contrastive loss는 배치가 클수록 유리하다
  (배치 안의 다른 샘플을 negative로 쓰므로 배치 8이면 negative가 7개뿐).
  여기에 코퍼스 쏠림(page 33이 76%)까지 겹치면 그 7개가 대부분 정답과 비슷할 수 있다.
  → **Stage 3에서 가장 아픈 제약이 될 가능성이 높다.**
- **교훈**: 문서에 "A가 B보다 빠르다"고 쓸 거면 **먼저 돌려보고 쓴다.**
  이번엔 실행해서 잡혔지만, 안 돌려봤으면 틀린 설명이 그대로 남았을 것이다.
