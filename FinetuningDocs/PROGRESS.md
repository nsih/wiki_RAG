### ★ 메모리 추정이 왜 빗나갔나

계산에서 **파이썬+torch 자체의 기본 점유를 빼먹었다.**

| 구간 | RSS |
|---|---|
| 파이썬 + torch import 직후 | **773 MB** ← 이걸 계산에 안 넣었음 |
| 모델 로드 후 | 810 MB (safetensors는 mmap이라 증가폭이 작다) |
| 학습 중 | **1,557 MB** |
| **피크** | **1,628 MB** |

즉 `가중치 422 + 학습분 331 = 753 MB`라는 계산 자체는 틀리지 않았다
(실제 학습 오버헤드 747 MB와 거의 일치). **베이스라인 773 MB를 누락한 것이다.**

**실무적 결론: 학습에는 여유 RAM이 최소 1.7 GB 필요하다.**
이 서버의 여유는 측정 시점에 따라 **1.4~2.4 GB**로 변동한다.
→ 학습 전 반드시 `free -m` 으로 확인하고, **Streamlit 앱을 내려야 한다.**
→ 1.4 GB 상황에서는 그대로 돌리면 **OOM으로 죽는다.**

**Stage 2 사전 검증 — 페이지 균형 샘플링이 실제로 되는가**

"된다"고 계획에만 적고 계산은 안 했다는 지적을 받아 실제로 확인했다.

*상한(cap)별 데이터 양 vs 균형 (100자 이상 청크 1,130개 기준)*

| cap | 총 청크 | 최대 페이지 비중 | 질문 2개 시 쌍 |
|---|---|---|---|
| 20 | 223 | 9.0% | 446 |
| **60** | **318** | **18.9%** | **636** |
| 100 | 364 | 27.5% | 728 |
| 무제한 | 1,130 | **76.6%** | 2,260 |

*배치 구성을 제약할 경우 (batch 8, 한 배치에 같은 페이지 금지)*

| cap | 완전 배치 수 | 활용률 |
|---|---|---|
| 30 | 32 | 99.2% |
| 60 | **33** | 83.0% |
| 무제한 | **33** | **23.4%** |

**→ cap을 아무리 풀어도 33배치가 상한.** 데이터가 아니라 **페이지 수 18개**에 걸린다.
(수식으로도 확인: 8B ≤ Σ min(nₚ, B) 를 만족하는 최대 B가 33)

*그래서 false negative가 실재하는지 측정했더니 전제가 틀렸다* → 위 결정 기록 참조.

**최종 방침**: `--max-per-page 60`(편향 대응) + 손실 마스킹(false negative 대응).
배치 구성은 제약하지 않는다. → **636쌍 / 79스텝/에폭 / 에폭당 약 1.5분**.

  - 18개 페이지를 순환 배분해 뽑는다(큰 페이지 독식 방지). `question`은 사용자가 채운다.

**Stage 2 검증 — `check_pairs.py` 작성**

"데이터가 잘못됐으면 어쩔 수 없되 검증은 하자"는 방침에 따라, 합성 질문을 숫자로 재는
스크립트를 따로 만들었다. 다섯 가지를 측정한다: 접지(구체 토큰이 청크에 실재하는가) /
저품질 청크 / 라벨 모순 / 베끼기 / BM25 자기검색.

**★ 검증기 자체의 오탐을 두 번 잡았다.** 검증 결과를 믿기 전에 검증기를 먼저 의심해야 했다.

| 오탐 | 증상 | 원인 | 수정 |
|---|---|---|---|
| 날짜 | "2020년 3월 11일"을 환각으로 판정 | 문서 표기는 `2020.03.11`. 문자열 그대로 비교하니 불일치 | 날짜 표기 5종 변형을 만들어 비교 |
| 저품질 청크 | 실데이터가 가득한 표(`page_22_chunk_0`)를 쓰레기로 판정 | `\|` 비율로 쟀는데 **이 코퍼스는 대부분이 마크다운 표**라 `\|`는 정상 신호다 | 목차 점선 비율 + 고유 내용어 수로 교체. 318청크로 임계값 보정 → 목차류 9개만 정확히 탐지 |

빈 셀(`||||||`) 비율도 기준으로 못 쓴다 — IP 대장은 비고 열이 원래 비어 있어서
정상 행 41개가 걸린다. 실제로 갈리는 건 점선과 내용어 수 두 가지뿐이었다.

*중간 측정 (36/318청크 시점, page 22·23에 편중된 표본이라 전량 수치는 다를 수 있다)*

| 검사 | 결과 |
|---|---|
| 접지 — 구체 토큰이 청크에 실재 | 86.5% (52개 중 45개) |
| └ 하나도 실재 안 함 (순수 환각) | 6.9% |
| └ 구체 토큰 자체가 없음 | 69.4% (일반 질문 — 다른 청크와 구분 약함) |
| 저품질 청크 | 9개 / 318 (2.8%) |
| **라벨 모순** | **0건** |
| **베끼기 (20자 이상 복사)** | **0쌍** (최장 연속 복사 중앙 8자) |
| BM25 자기검색 | Recall@1 53.8% / @5 92.3% / 20위 밖 1.9% |

→ PLAN 8절 1항이 우려한 "합성 질문이 청크를 베껴 점수를 부풀린다"는 **어휘 수준에서는
관측되지 않았다.** 대신 구체 토큰 없는 일반 질문 비중이 문제로 보인다.
환각 쌍 제외는 `--drop` 으로 가능하나, **전량 수치를 보고 결정한다** (지금 정하면
page 23에 판단이 끌려간다).

**사람용 평가셋 — Claude가 대신 작성 (사용자 요청)**

`eval_human.jsonl` 40문항을 작성했다. **원래 이 파일은 사용자가 직접 쓰기로 한 것이다**
(LLM이 쓴 질문은 문서 표현을 베껴 점수를 부풀리므로 — PLAN 8절 1항).
사용자 요청으로 Claude가 대신 썼고, 각 줄에 `"author": "claude-opus-5"` 를 박아 출처를 남겼다.

한계를 줄이려고 한 것:
- 청크 원문 40개를 전부 읽고, **문서 표현을 베끼지 않고 검색창 말투로** 썼다
  (예: "정보전산원 몇 호관에 있어", "물품 대금 며칠 안에 줘야 해"). 평균 19자.
- 답이 두 청크에 똑같이 있는 경우(사무분장표 ↔ 정보전산원 소개 등) `also_ok` 필드로
  복수 정답을 명시했다. 4줄. 평가 시 어느 쪽을 찾아도 정답으로 친다.

*BM25 난이도 비교 (후보 318청크)*

| 평가셋 | Recall@1 | Recall@5 |
|---|---|---|
| eval_human (Claude 작성, 검색어 말투) | 52.5% | **82.5%** |
| 합성 eval (qwen3-4b, 중간 표본) | 53.8% | 92.3% |

Recall@5가 10%p 낮다 = **어휘 매칭만으로는 안 잡히는 질문이 7개** 있다는 뜻이고,
그 자리가 임베딩 파인튜닝이 기여할 수 있는 지점이다. 평가셋으로는 합성셋보다 낫다.
