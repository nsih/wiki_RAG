## 1. 무엇을 왜 했나

사내 위키 검색이 약했다. 검색 방식이 두 개인데, 둘 중 하나가 제 역할을 못 하고 있었다.

| 방식 | 원리 | 상태 |
|---|---|---|
| **BM25** | 질문의 단어가 문서에 몇 번 나오는지 세서 점수를 매김 | 잘 작동 |
| **벡터 검색** | 문장을 숫자로 바꿔서 **숫자가 비슷한 문서**를 찾음 | 거의 작동 안 함 |

원인을 "이 모델이 우리 학교 용어를 배운 적이 없어서"로 보고 **우리 문서로 추가 학습**시켰다.
기존에 쓰던 `jhgan/ko-sroberta-multitask`(범용 한국어 임베딩 모델)를 그대로 가져와
일부만 고치는 방식이다.

## 2. 벡터 검색이란

문장을 **768개짜리 숫자 배열**로 바꾼다. 이걸 임베딩이라 한다.

```
"정보전산원 어디 있어"    →  [0.21, -0.05, 0.88, ... ]
"정보전산원은 1호관 3층"  →  [0.19, -0.02, 0.91, ... ]
```

두 배열이 닮은 정도는 **코사인 유사도**로 잰다.
길이를 1로 맞춘(정규화) 두 벡터의 **내적**이 곧 코사인값이다.

```python
sim = a @ b     # 정규화했으면 내적 = cos(각도). 1에 가까울수록 유사
```

검색은 질문 벡터와 1,136개 문서 벡터를 전부 내적해서 높은 순으로 줄 세우는 것이다.

문장 하나를 768개 숫자로 어떻게 바꾸는가 — 모델이 단어(토큰)마다 벡터를 하나씩 내놓고,
그걸 **전부 평균**낸다. 이걸 mean pooling이라 한다. **뒤에 나올 실패 원인이 여기 있다.**

## 3. 학습을 어떻게 시켰나

핵심은 **8지선다 문제 풀리기**다.

질문 8개와 정답 문서 8개를 한 묶음(배치)으로 넣고 8×8 유사도 표를 만든다.
1번 질문의 정답은 1번 문서, 2번은 2번… **대각선이 정답**이다.
"각 줄에서 대각선이 제일 높게 나오도록 고쳐라"가 학습 목표다.

```python
sim = (q @ d.T) * 20                          # 8x8 유사도 표
loss = F.cross_entropy(sim, torch.arange(8))  # 정답은 대각선
```

분류 문제에서 쓰는 `cross_entropy`를 그대로 쓴다.
**오답을 따로 준비할 필요가 없다**는 게 이 방식의 장점이다 —
배치 안의 나머지 7개가 자동으로 오답 역할을 한다. (in-batch negative)

| 세부 | 이유 |
|---|---|
| 왜 20을 곱하나 | 코사인은 −1~1이라 그대로 softmax에 넣으면 확률이 밋밋해져 학습 신호가 약하다. 20을 곱해 차이를 벌린다 |
| **같은 페이지는 오답에서 제외** | 8개 중 같은 문서에서 나온 조각이 섞이면 오답이 아닌데 오답 취급된다. 그 칸을 `-10000`으로 덮어 제외한다(3줄) |
| 손실이 얼마면 잘된 건가 | 찍어서 맞히면 `ln(8) = 2.08`이다. 실제로는 **0.439 → 0.195**까지 내려갔다 |

전체 학습 시간 **20분**(2회 반복, 110스텝).

## 4. 메모리 때문에 일부만 학습했다

모델은 1억 1천만 개 파라미터다. 전부 학습하려면:

```
가중치        110M × 4바이트 =  440 MB
기울기        110M × 4바이트 =  440 MB
Adam 내부상태 110M × 8바이트 =  880 MB
                             ─────────
                               1,760 MB   ← 가용 메모리 초과
```

Adam은 파라미터마다 값 2개(기울기의 평균·분산 추정치)를 들고 있어서 가중치의 2배를 먹는다.
그래서 **12개 층 중 위 4개만 학습**하고 나머지는 얼렸다(28.4M, 전체의 25.6%).

이건 타협이 아니라 정석이다. 아래층은 한국어 문법 같은 일반적인 것을,
**도메인 적응은 주로 위층**이 담당한다. 데이터가 442쌍뿐일 때 전체를 학습하면 과적합 위험이 크다.

> 실측 1,593MB로 예상(930MB)보다 컸다.
> 파이썬+torch를 켜기만 해도 773MB인데 계산에 안 넣었다.

## 5. 학습 데이터가 없어서 만들었다

"이 질문의 정답은 이 문서"라는 정답지가 필요한데 없었다.
**문서를 LLM에게 보여주고 질문을 만들게** 했다(doc2query).

문제가 하나 있었다. 조각 1,136개 중 **867개(76%)가 `IP 주소 대장` 한 페이지**였다.
그대로 두면 학습이 그쪽으로 쏠린다.

| 처리 | 결과 |
|---|---|
| 페이지당 최대 60조각 제한 | 318조각, 최대 비중 **76% → 19%** |
| 조각당 질문 2개 생성 | **630쌍** |
| 품질 검사 후 불량 제외 | **548쌍** |
| 학습용 / 시험용 분리 | 442 / 106 |

**품질 검사에서 가장 중요한 건 "LLM이 원문을 베꼈나"** 다.
베끼면 모델이 검색이 아니라 문자열 맞추기를 배우고 시험 점수만 오른다.
20자 이상 연속 복사는 **4.4%**, 최장 29자로 통째 복사는 없었다.

**분리는 반드시 조각 단위**여야 한다. 한 조각에서 질문 2개가 나오므로
질문 단위로 섞으면 같은 조각이 학습용과 시험용에 갈려 **시험지를 미리 본 셈**이 된다.

## 6. 평가는 실제로 어떻게 하나

재료는 세 가지다.

| 재료 | 내용 |
|---|---|
| 평가할 모델 | 학습 전(baseline) 또는 학습 후(ft-ep2) |
| 시험지 | `(질문, 정답 조각 ID)` 목록 |
| 후보 풀 | 검색 대상 전체 1,130조각 |

**정답지가 어디서 왔나**가 중요하다. 질문을 만들 때 **보여준 조각이 곧 정답**이다.
`page_22_chunk_4`를 보여주고 질문을 쓰게 했으니 그 질문의 정답은 정의상 그 조각이다.

### 절차 5단계

**① 후보 1,130개를 전부 벡터로 변환** — `(1130, 768)` 행렬. CPU에서 약 4분.

**② 질문도 같은 모델·같은 함수로 변환** — `(40, 768)`.
문서와 질문의 인코딩 방식이 다르면 좌표계가 어긋나 비교가 무의미해진다.

**③ 행렬곱 한 번으로 전체 유사도 계산**

```python
sim = Q @ D.T     # (40,768) @ (768,1130) = (40,1130)
```

40개 질문 × 1,130개 조각 = 45,200개 점수가 한 번에 나온다.

**④ 정답의 순위 구하기** — 전체를 정렬하지 않는다.

```python
best = sim_row[정답_인덱스]                 # 정답 조각의 점수
rank = 1 + (sim_row > best).sum().item()   # 그보다 높은 게 몇 개?
```

**정답보다 점수가 높은 조각 개수 + 1 = 정답의 순위**다. 정렬보다 세는 게 빠르다.
두 가지 처리가 들어간다 — `>` 이므로 **동점은 정답보다 앞선 것으로** 본다
(점수를 후하게 주지 않으려고). 그리고 사무분장표처럼 **같은 내용이 두 조각에 있는 경우**(4문항)는
둘 다 정답으로 두고 더 높은 순위를 채택한다.

**⑤ 순위 목록을 점수로 환산**

40문항의 순위가 `[1, 3, 1, 99, 2, ...]` 라면:

| 지표 | 계산 | 의미 |
|---|---|---|
| R@1 | 순위가 1인 비율 | 정답이 맨 위에 온 비율 |
| R@5 | 순위가 5 이하인 비율 | **앱이 상위 5개를 LLM에게 넘기므로 가장 실질적** |
| MRR@10 | 순위 역수의 평균 (10위 밖은 0) | 1위=1점, 2위=0.5점, 5위=0.2점 |

**예시**: `"정보전산원 몇 호관에 있어"`의 정답이 1위면 R@1 ✓, R@5 ✓, MRR 1.0점.
7위였다면 R@1 ✗, R@5 ✗, MRR 0.14점.

### BM25와 하이브리드도 같은 방식

시험지·후보 풀·순위 계산은 그대로 두고 **점수 매기는 방법만** 바꾼다.

| 방식 | 점수 |
|---|---|
| 벡터 | 코사인 유사도 |
| BM25 | 단어 빈도 기반 점수 |
| 하이브리드 | 두 순위를 `1/(60+순위)`로 합산 |
| 2단계 | 벡터로 페이지 3개 선택 → 그 안에서 BM25 점수로 정렬 |

## 7. 시험 설계에서 조심한 것

지표 계산보다 **조건 설계**가 결과를 좌우한다.

| 결정 | 안 그랬다면 |
|---|---|
| 후보를 1,130개 전부로 | 학습에 쓴 318개로만 재면 답 찾기가 쉬워져 점수가 뻥튀기 |
| **벡터만으로** 채점 | BM25를 섞으면 BM25가 잘해서 모델이 나빠져도 티가 안 남 |
| 시험지 2종 | LLM이 만든 문제만 보면 "원문 찾기"를 외운 건지 구분 못 함 |
| 두 모델이 같은 코드를 타게 | 모델 차이인지 구현 차이인지 구분 불가 |

전체 평균 외에 **페이지별 점수와 그 평균**도 같이 봤다.
`IP 주소 대장`이 코퍼스의 76%라 전체 평균은 사실상 그 페이지 점수이기 때문이다.
둘을 같이 봐야 "IP 대장만 좋아지고 나머지는 망가진" 경우를 잡아낸다.

## 9. 결론이 뒤집힌 지점

앱은 BM25와 벡터를 합쳐 쓰는데, 합친 상태로 재니
**사람 시험지 MRR이 50.6 → 50.6으로 똑같았다.** 벡터만으로는 +7.5였는데 사라졌다.
그래서 처음엔 "쓸모없다"고 결론 냈다.

그런데 **채점 기준**을 바꿔보니 정반대였다.

| 채점 기준 | 학습 전 | 학습 후 | BM25 |
|---|---|---|---|
| 정확한 **조각**을 찾았나 | 47.5 | 55.0 | **77.5** |
| 맞는 **문서**를 찾았나 | 85.0 | **95.0** | 90.0 |

**문서 단위로는 학습한 모델이 1등이다.** 두 방식이 잘하는 층위가 다르다.

- **BM25**: 정확한 행 찍기. `100.100.120.154` 같은 건 단어 매칭이 압도적
- **벡터**: 맞는 문서 찾기. 단 IP 대장의 인접 행들은 벡터가 거의 똑같아 구분 불가

즉 조각 단위 채점은 **벡터에게 구조적으로 불리**했다. 의미상 같은 옆 행을 가져와도 오답이니까.

## 10. 그럼 어떻게 합쳐야 하나

현재 앱은 순위만 보고 더한다.

```
점수 = 1/(60 + BM25순위) + 1/(60 + 벡터순위)
```

서로 다른 척도(BM25 점수 vs 코사인)를 정규화 없이 합칠 수 있다는 게 장점이지만,
대가로 **각 방식이 얼마나 믿을 만한지를 전혀 안 본다.** 잘하는 쪽이 못하는 쪽에 끌려 내려간다.

역할을 나눠 순서대로 시켜봤다 — **벡터로 문서 3개를 고르고, 그 안에서 BM25로 행 찍기**.

| 방식 | 사람 시험지 R@5 |
|---|---|
| 현재 앱 (합산) | 72.5 |
| 모델만 바꿈 | 75.0 |
| 구조만 바꿈 | 75.0 |
| **둘 다 바꿈** | **82.5** |

**한쪽만 바꾸면 +2.5인데 둘을 합치면 +10.0이다.**
2단계 방식은 "벡터가 문서를 정확히 고른다"에 기대는 구조라,
그 능력을 85% → 95%로 올린 파인튜닝이 있어야 값을 한다.

## 11. 실패 분석 — "7호관"

"7호관 아이피 대역"을 물으면 학습한 모델이 **6호관·1호관**을 가져온다(10/10 → 0/10).

원인을 찾았다. 결과 10개의 `(호관, 층)` 조합이 **10개 전부 층 칸에 7을 포함**했다 —
`6호관|5,6,7,8`, `1호관|7,8,9`. 즉 **숫자 7을 "호관"이 아니라 "층"과 맞추고 있다.**

2절의 mean pooling이 원인이다. 토큰 벡터를 전부 평균내면
**"이 숫자가 몇 번째 칸에 있었는지"가 사라진다.** 표의 열 구분은 벡터에 남을 방법이 없다.

**파고들다 더 큰 걸 발견했다.**

```python
tokenize_ko('7호관 아이피 대역')  →  ['호관', '아이피', '대역']
```

앱의 단어 분리 코드가 한글과 숫자를 따로 끊고 1글자 토큰을 버려서
**"7호관"의 7이 사라진다.** BM25에게 1호관·7호관·9호관이 전부 같은 단어다.
숫자가 없는 "별관"만 잘 맞는 게 증거다.

이건 AI 학습과 **무관한 버그**이고 코드 몇 줄로 고칠 수 있다.

## 12. 통계적으로 어디까지 말할 수 있나

같은 질문에 두 방식을 적용한 결과이므로, **한쪽만 맞힌 문항**만 세면 된다.

| 시험지 | 현재앱만 맞힘 | 새 방식만 맞힘 | 우연일 확률(p) |
|---|---|---|---|
| LLM 문제 (106) | 2 | 24 | **0.00001** |
| 사람 문제 (40) | 0 | 4 | 0.125 |

사람 시험지의 0.125는 **결과가 약해서가 아니라 문항이 적어서**다.
갈린 문항이 4개면 **4개가 전부 한쪽이어도** 하한이 0.125라
통상 기준(0.05)에 도달할 수 없다. 약 100문항이면 가능하다.

LLM 시험지의 0.00001도 액면대로 믿으면 안 된다. 이 시험지는 품질 검사에서
**BM25가 못 찾는 문항을 미리 걸러내고** 만들었으므로 BM25에 유리하게 치우쳐 있다.

**말할 수 있는 선**: 개선 방향은 두 시험지에서 일관되고,
사람 시험지에서 **더 틀린 문항이 0개**다. "측정한 범위에서 개선됐다"까지다.

---

## 13. 정리

| 질문 | 답 |
|---|---|
| 파인튜닝은 성공했나 | **성공.** 벡터 검색이 두 시험지 모두 올랐고, 문서 찾기는 BM25도 넘었다 |
| 왜 앱에 안 넣었나 | 합친 상태의 개선이 확실하지 않고, 더 싸게 고칠 게 먼저 나왔다 |
| 아쉬운 점의 원인 | ①② 데이터 성질(표·식별자는 단어 검색의 영역) ③ mean pooling의 한계 ④ 시험지 40문항 |
| 다음 우선순위 | **① 단어 분리 코드 → ② 합치는 방식 → ③ 모델** |

①이 1순위인 이유는 가장 싸고, 파인튜닝과 무관하며, **②의 성능 상한을 결정**하기 때문이다.
2단계 방식은 문서 안에서 행 고르는 일을 BM25에 맡기므로 BM25의 단어 분리 품질이 곧 천장이 된다.
